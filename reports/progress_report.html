Lexsi Labs AI Safety & Alignment Hackathon 2026 · Track 3 · Round 1

RewardShield: how much verifier precision does a small SQL agent need?

A controlled study of reward verifiers for a text-to-SQL agent built on Tiny Aya Global. We measure how often each verifier rewards a wrong query, what it costs to run, and whether training on more precisely filtered data makes the agent better.

In one paragraph. All P0 experiments are done and the three pre-registered hypotheses are tested. On 1,360 oracle-labelled dev-A samples, the targeted verifier wrongly accepts 1.39% of what it accepts, against 3.88% for the single-database check (H1 supported) and 3.13% for random databases at the same cost (H2 supported). Fine-tuning on targeted-accepted data did not beat fine-tuning on single-accepted data on held-out dev-B: 62.0% vs 63.1%, difference −1.1 points [−4.2, +1.9] (H3 inconclusive), because the two training sets differ in only about 4% of their examples. Overall the agent went from 51.5% (base) to 62.0–63.1% on dev-B. Overnight we also found and fixed a bug where the warm-start model invented tool results.

The research problem

When an agent is trained with rewards, the reward check decides what the agent learns. For SQL the usual check runs the predicted query on one database and compares the rows with the gold query's rows. A wrong query can still return the right rows on that one database, so the check passes it. ReViSQL (Zhu et al. 2026) found that 32.8% of positive single-database rewards for a large model were refuted by a formal checker.

Nobody has measured, for a small model, how much a more precise check is worth: how many false rewards it removes, what it costs, and whether it changes what the model learns.

A false accept, illustrated

An illustrative pair, not taken from our data. Both queries return the same rows on the original Spider database because no visitor is exactly 30. A single-database verifier rewards the wrong query; a test database that contains a 30-year-old exposes it.

gold
SELECT count(*) FROM visitor
WHERE age > 30
predicted (wrong, accepted)
SELECT count(*) FROM visitor
WHERE age >= 30

Our oracle sanity check found exactly this kind of miss: the original database alone failed to reject 8 of 50 hand-made wrong queries, 4 of them flipped comparisons on museum_visit.

Our solution

Three verifiers, one oracle, matched training arms

We score one shared pool of agent rollouts with several verifiers, label the same pool with an independent oracle, and then fine-tune separate copies of the agent on the samples each verifier accepted. The arms differ only in which verifier chose their data.

H1

Targeted-4 has a lower false-accept share than single-1 on the dev-A audit pool.

H2

Targeted-4 has a lower false-accept share than random-4, with the same number of databases.

H3

The arm trained on targeted-4-accepted samples beats the single-1 arm on held-out dev-B test-suite accuracy.

How the comparison is kept fair

  • Hypotheses, sample sizes and the arm-building rule were written down before any sampling.
  • Splits are schema-disjoint: warm start, training pool, dev-A (audit) and dev-B (held-out) share no databases.
  • Arms get the same example count, steps (100 × 16), seed and starting checkpoint.
  • 95% intervals come from 10,000 paired bootstrap resamples over questions, with a schema-level bootstrap alongside. Gaps under 2 points count as no practical difference.

What we will not claim

  • Not a new verification method; targeted test databases come from Zhong et al. 2020.
  • Not online RL or GRPO; training is reward-filtered supervised fine-tuning.
  • Agreement on a finite test suite is not proof of semantic equivalence.
  • No claim beyond Spider easy/medium questions and Tiny Aya Global.

Blockers and challenges

What got in the way

needs you open risk resolved

Publishing permission needs you at Phase 6

HF is logged in as shro-2002. Before anything goes public (HF collections, GitHub repo, upstream AgentTune issue) I will ask you once.

Warm-start model invented tool results fixed

Every E01 turn ran on past its tool call and wrote a fake Tool result. Causes: generation never stopped at the chat template's end-of-turn token, and the warm-start loss covered tool-result turns. Fixed both before any pool sample was kept; rollouts dropped from 384 to about 75 tokens. Re-runs show the earlier accuracy numbers were unaffected.

Kaggle queue and GPU memory resolved

The first pool job sat queued 3.5 h; the account runs one GPU job at a time. Split jobs on 2×T4 ran instead. The longest prompts ran out of memory at batch 16; 18 baseball_1 questions were excluded because their prompt alone exceeds the pre-registered 3,072-token training limit.

Local Mac GPU as fallback assessed

MPS works but is far too slow for the pool or training (5.5 rollouts/min after the fix; batch 16 ran out of memory). Used only for scoring, oracle labels and analysis.

GPU quota unverified

Kaggle allows 30 GPU hours a week, and this account ran out once already this week. The remaining P0 work needs roughly 4.3 h (pool) + 2 h (two arms) + 1 h (evaluation). I could not read the current balance: the Kaggle connector is not signed in.

Oracle is a rebuild, not the official suite declared limitation

The official Spider test suites were blocked by a Google Drive quota. We regenerated them with the original authors' generator (2 to 12 databases per schema instead of about 1,000), so the oracle may be somewhat lenient on rare cases. Declared as a deviation before any sampling; the generator has no licence, so the databases will not be redistributed.

Crowded field bounds the novelty claim

There is already a strong Tiny Aya SQLite agent entry, and ReViSQL, Zhong et al., ParSEval, VeriEQL and XData cover verification itself. Our claim is limited to the controlled small-model comparison.

Oracle build filled the disk resolved

The generator wrote a 54 GB candidate pool because it never VACUUMs deleted tables. Fixed in our own scripts (VACUUM, caps, a watchdog); the final suite is 104 MB.

Training crashes on Kaggle resolved

TRL 1.7 removed warmup_ratio; then the trainer wrapped the model in DataParallel across two T4s and crashed. Switched to explicit warmup steps and torchrun DDP with the same effective batch.

Finished job marked ERROR resolved

E01 completed, but one harmless last-line command failed, and Kaggle refuses an ERROR kernel as input to the next job. Uploaded the adapter as a private dataset and added --datasets to the runner.

Base model formatting resolved

The first smoke run made 0 of 2 valid tool calls. On the full dev sets the base model commits SQL in 74–80% of episodes, and the warm start raises that to 81–84%.
